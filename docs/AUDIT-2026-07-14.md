# transcript-app — Audit 2026-07-14

> **Fork policy**: This repo is a fork of `jbennygold/transcript-app`. We do not maintain application code here. This audit documents findings for upstream awareness; no source-code changes are made in this fork.

---

## Critical

### C-1 · `/api/rebuild` is unauthenticated
**File:** `src/app/api/rebuild/route.ts`  
**Finding:** The rebuild endpoint triggers a full index rebuild (re-embedding all transcript segments into the Vercel Blob vector store) with no authentication. Any internet-accessible caller can trigger an expensive, time-consuming operation. This can exhaust Anthropic/OpenAI embedding quotas and cause prolonged UI unavailability.  
**Recommended fix (upstream):** Require a `CRON_SECRET` or admin session token. The simplest approach: compare `request.headers.get('Authorization')` against a secret stored in an environment variable before proceeding.

### C-2 · AssemblyAI webhook has no signature verification
**File:** `src/app/api/webhooks/assemblyai/route.ts`  
**Finding:** The webhook endpoint for AssemblyAI transcription callbacks does not verify the `x-assemblyai-signature` header (HMAC-SHA256). Any caller can POST a forged transcript to this endpoint, injecting arbitrary text into the search index.  
**Recommended fix (upstream):** Verify the `x-assemblyai-signature` header against the webhook secret from AssemblyAI's documentation before processing the payload.

## High

### H-1 · BM25 index is rebuilt from scratch on every search
**File:** `src/lib/search.ts` (or equivalent BM25 implementation)  
**Finding:** BM25 term-frequency statistics are recomputed over the full corpus on every search request. For a large transcript library this adds significant latency to each query.  
**Recommended fix (upstream):** Pre-build and cache the BM25 index at startup (module-level singleton). Invalidate and rebuild only when `/api/rebuild` runs successfully.

### H-2 · Vector search results are not deduplicated before RRF fusion
**File:** `src/lib/search.ts`  
**Finding:** If the same transcript segment appears in both the BM25 and vector result sets, it may be counted twice (or with unbalanced weight) in the RRF fusion step rather than being merged at its deduplicated score.  
**Recommended fix (upstream):** Deduplicate by segment ID before RRF scoring; accumulate reciprocal ranks across both lists for shared IDs.

## Medium

### M-1 · No rate limiting on search or rebuild endpoints
**Finding:** Both `/api/search` and `/api/rebuild` (and `/api/ask` if present) are unthrottled. A single client can exhaust embedding quotas via the rebuild endpoint or produce excessive AI costs via repeated search queries.  
**Recommended fix (upstream):** Apply a per-IP rate limiter (e.g., 60 search requests/minute, 1 rebuild/hour).

### M-2 · Transcript upload stores files in Vercel Blob without size validation
**Finding:** The upload route does not enforce a maximum file size before writing to Vercel Blob. Very large files can cause Lambda timeouts or unexpected storage costs.  
**Recommended fix (upstream):** Reject uploads exceeding a configured maximum (e.g., 10 MB) with HTTP 413 before reading the body.

### M-3 · No error boundary for transcript rendering
**Finding:** If a stored transcript is malformed (missing `segments` array, unexpected field types), the rendering component will throw an uncaught error rather than showing a graceful fallback.  
**Recommended fix (upstream):** Add a try/catch around segment parsing and display a "Could not render transcript" fallback UI.

## Low

### L-1 · No test suite
**Finding:** Zero automated tests. Core search logic (BM25, RRF, hybrid retrieval) is algorithmically non-trivial and particularly suited to regression tests.

### L-2 · `package.json` dependency audit not run
**Finding:** Dependency freshness not assessed in this audit cycle (fork policy prevents running `npm audit` and acting on findings).  
**Recommended action (upstream):** Run `npm audit --audit-level=high` and address any high/critical findings.
